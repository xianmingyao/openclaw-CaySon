## 二、MCP适配层深度分析

### 2.1 为什么字节必问MCP？

**面试考察点**：MCP是2024-2025年工具调用领域的重大演进，字节作为工具平台型公司，考察MCP是在看候选人对**工具治理**的理解深度。

**传统工具调用 vs MCP**：

| 维度 | 传统Function Calling/Tool Use | MCP (Model Context Protocol) |
|------|------------------------------|----------------------------|
| **协议标准** | 各家私有，OpenAI/Claude/Anthropic各不同 | 统一协议，一次开发到处运行 |
| **工具发现** | 硬编码工具列表 | 动态发现，工具主动注册 |
| **权限控制** | 业务代码里散落 | 协议层统一管理 |
| **调用审计** | 无标准化日志 | 内置调用记录 |
| **超时治理** | 手动处理 | 协议层统一处理 |
| **版本管理** | 无 | 工具版本化，可回滚 |

**→ 关联Ontology**：MCP适配层本质上是**工具层面的Ontology**——定义了工具的"Schema"（参数类型/权限/描述）和"实例"（具体工具实现）。

### 2.2 MCP工程实现关键细节

```python
# MCP Server注册与发现机制
class MCPServer:
    def __init__(self, name: str, version: str):
        self.name = name
        self.version = version
        self.tools: Dict[str, Tool] = {}
        self.capabilities = []
    
    def register_tool(self, tool: "Tool"):
        """工具注册：名称、参数Schema、权限级别"""
        self.tools[tool.name] = tool
        # 发布到MCP Registry
        MCP_REGISTRY.publish(self.name, tool.name, tool.schema)
    
    def deregister_tool(self, tool_name: str):
        """工具下线：优雅退出，不影响正在执行的调用"""
        self.tools.pop(tool_name, None)
        MCP_REGISTRY.unpublish(self.name, tool_name)

# MCP Client调用链
class MCPClient:
    def call_tool(self, tool_name: str, params: dict) -> Any:
        # 1. 权限检查（协议层）
        if not selfPermissionService.check(tool_name, params):
            raise PermissionDenied(tool_name)
        
        # 2. 参数校验（Schema Validation）
        schema = MCP_REGISTRY.get_schema(tool_name)
        validated_params = schema.validate(params)
        
        # 3. 超时控制（协议层）
        timeout = MCP_REGISTRY.get_timeout(tool_name)
        
        # 4. 执行 + 审计日志
        start = time.time()
        try:
            result = self._execute(validated_params, timeout)
            self._audit_log(tool_name, params, result, success=True)
            return result
        except TimeoutError:
            self._audit_log(tool_name, params, None, success=False, error="timeout")
            raise
        finally:
            # 5. 资源清理
            self._cleanup(tool_name)
```

**MCP三大特性**：
- **可插拔**：工具随时注册/下线，Agent无需重启
- **可治理**：权限/审计/限流在协议层统一管理
- **可扩展**：新工具无需修改Agent核心代码

## 三、模型写库：工具执行的工程实践

### 3.1 为什么字节把"写库"单独考察？

**面试考察点**：大模型生成的内容**写入会产生副作用**，这是生产环境最危险的地方。字节考察的是候选人是否理解"AI生成≠AI执行"的分离架构。

**读库 vs 写库的本质区别**：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    读库 vs 写库：副作用的对称性                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   读库（查询/检索）              写库（增/删/改）                     │
│   ┌──────────────┐              ┌──────────────┐                   │
│   │ 无副作用       │              │ 有副作用      │                   │
│   │ 查错最多白跑   │              │ 写错会破坏数据 │                   │
│   │ 可幂等重试    │              │ 需要事务控制   │                   │
│   └──────────────┘              └──────────────┘                   │
│                                                                      │
│   AI只生成意图              AI生成意图 + 结构化参数                  │
│   人工/系统校验后执行        后端必须二次校验                          │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 写库工程实现：五层校验

```python
# 写库五层校验架构（LangChain Agent生产实践）
class ToolWriteExecutor:
    """
    模型写库执行器：AI生成意图 → 后端五层校验 → 执行
    """
    
    # 第一层：参数Schema校验
    def validate_params(self, tool_name: str, raw_params: dict):
        schema = get_tool_schema(tool_name)
        return schema.validate(raw_params)  # 类型/必填/格式
    
    # 第二层：业务权限校验
    def check_permission(self, user_id: str, tool_name: str, params: dict):
        """
        RBAC：用户角色 → 工具权限矩阵
        问自己：这个用户有没有权限调用这个工具操作这个数据？
        """
        user_role = get_user_role(user_id)
        data_scope = get_data_scope(user_id, tool_name)
        
        # 金额超限？数据归属？操作类型？
        if not self.rbac_service.can_access(user_role, tool_name, params):
            raise PermissionDenied(f"User {user_id} cannot {tool_name}")
    
    # 第三层：业务规则校验（本体规则引擎）
    def check_business_rules(self, tool_name: str, params: dict):
        """
        本体规则兜底：金额>100万→总监审批
        这个规则对AI和人工一视同仁
        → 关联Ontology：规则引擎是本体的执行层
        """
        rules = get_rules_for_tool(tool_name)
        for rule in rules:
            if rule.matches(params):
                if rule.requires_approval:
                    # 写入审批流，不直接执行
                    submit_for_approval(params, rule)
                    return ApprovalStatus.PENDING
                elif not rule.can_proceed(params):
                    raise BusinessRuleViolation(rule.name)
    
    # 第四层：风险确认（高风险操作）
    def risk_confirmation(self, tool_name: str, params: dict) -> bool:
        """
        高风险操作需要二次确认：
        - 删除操作
        - 金额>10万
        - 涉及多个系统
        - 修改客户核心数据
        """
        risk_level = self.assess_risk(tool_name, params)
        if risk_level == RiskLevel.HIGH:
            # 发送确认请求给用户
            send_confirmation_request(user_id, tool_name, params)
            return False  # 等待用户确认
        return True
    
    # 第五层：事务控制
    def execute_with_transaction(self, tool_name: str, params: dict):
        with self.db.transaction():
            result = self.execute_write(tool_name, params)
            # 审计日志（事务成功后）
            self.audit_log(tool_name, params, result)
        return result
```

```
AI的强项是'想'，但'做'必须有人兜底。"
```

#### 4.2.1 文档切块：策略选择

```python
# 切块策略对比
class ChunkingStrategies:
    """
    生产中常见的切块策略，各有优劣：
    """
    
    # 策略1：固定大小切块（简单但效果一般）
    def fixed_size_chunk(self, text: str, chunk_size: int = 500, 
                         overlap: int = 50) -> List[str]:
        """简单的字符级别切块"""
        chunks = []
        for i in range(0, len(text), chunk_size - overlap):
            chunks.append(text[i:i+chunk_size])
        return chunks
        # 问题：可能切断句子、段落语义
    
    # 策略2：语义切块（推荐生产使用）
    def semantic_chunk(self, text: str, 
                       tokenizer: Callable) -> List[str]:
        """
        按语义段落切块，保持上下文完整
        使用NLP句子分割 + 长度控制
        """
        sentences = self.sentencize(text)  # NLP句子分割
        chunks = []
        current_chunk = []
        current_tokens = 0
        
        for sent in sentences:
            sent_tokens = len(tokenizer(sent))
            if current_tokens + sent_tokens > 500:
                # 当前块满了，保存并开始新块
                chunks.append(" ".join(current_chunk))
                # overlap：保留上最后一句保证连续性
                current_chunk = [current_chunk[-1], sent] if current_chunk else [sent]
                current_tokens = len(tokenizer(current_chunk[-1]))
            else:
                current_chunk.append(sent)
                current_tokens += sent_tokens
        
        if current_chunk:
            chunks.append(" ".join(current_chunk))
        return chunks
    
    # 策略3：层级切块（适合长文档）
    def hierarchical_chunk(self, document: "Document") -> List[str]:
        """
        先按章节切，再按段落切
        保留文档层级结构信息
        """
        chapters = self.split_by_headings(document, level=1)
        chunks = []
        for chapter in chapters:
            # 章节级别chunk
            chunks.append(chapter.text)
            # 段落级别chunk（更细粒度检索）
            paragraphs = self.split_by_headings(chapter, level=2)
            for para in paragraphs:
                if len(para.text) > 50:  # 过滤短段落
                    chunks.append(para.text)
        return chunks
```

**→ 字节面试追问**：chunk_size选多少？怎么决定？

```

"chunk_size没有万能值，通常500-1000 tokens是经验值。
但关键不是固定值，是'保持语义完整性'。

我通常用几个策略组合：
1. 先用NLP句子分割，保持句子不断开
2. 按语义段落切块，避免把相关的内容切断
3. 重叠50-100 tokens，保证块之间的连续性
4. 保留文档结构（标题/层级），检索时能还原上下文
```

#### 4.2.3 Rerank重排：最被忽略的环节

```python
# Rerank实现：两阶段检索的关键
class Reranker:
    """
    第一阶段：向量召回（快但粗糙）
    第二阶段：Rerank（精但慢）
    
    为什么需要Rerank？
    - 向量相似度≠语义相关性
    - 向量模型是双编码器，上下文融合有限
    - Rerank是Cross-Encoder，效果更准
    """
    
    def rerank(self, query: str, retrieved_docs: List[dict], 
               top_k: int = 5) -> List[dict]:
        """
        常用Rerank模型：
        - BAAI/bge-reranker-v2-m3（国产，支持中文）
        - cross-encoder/ms-marco-MiniLM-L-12-v2（轻量）
        - jinaai/jina-reranker-v1-base-en（多语言）
        """
        pairs = [(query, doc["content"]) for doc in retrieved_docs]
        
        # 调用Rerank模型（通常<100ms，比生成快）
        scores = self.rerank_model.predict(pairs)
        
        # 按分数排序
        ranked = sorted(
            zip(retrieved_docs, scores), 
            key=lambda x: x[1], 
            reverse=True
        )
        
        return [doc for doc, score in ranked[:top_k]]
```

**→ 字节面试加分项**：Rerank vs 直接增加召回量

```
面试官：为什么不直接召回更多向量，用Rerank有什么好处？

满分回答：
"这是个好问题。很多人觉得多召回一些不就得了？

但向量检索有两个根本局限：
1. 双编码器局限：向量模型把query和doc分别编码再算相似度，
   上下文融合不够。Cross-Encoder的Rerank能弥补这个。
2. top-K的K怎么选：K小了可能漏，K大了引入噪声。

Rerank的工程价值：
- 向量召回：快速海选，从10000个里选出100个候选（<50ms）
- Rerank：精挑细选，从100个里选出最相关的10个（<100ms）
- 总延迟<150ms，但效果提升显著（MRR@10通常提升20-30%）

简单说：向量召回是'广撒网'，Rerank是'精准捞'。"
```

### 5.2 短期记忆：上下文压缩

```python
class ShortTermMemory:
    """
    短期记忆：当前会话，存储在内存/Redis
    核心问题：上下文越来越长，怎么办？
    """
    
    def __init__(self, max_tokens: int = 128000):
        self.max_tokens = max_tokens  # GPT-4-Turbo=128K, GPT-3.5=16K
        self.messages = []  # 消息列表
    
    def add_message(self, role: str, content: str):
        self.messages.append({"role": role, "content": content})
    
    def should_compress(self) -> bool:
        """压缩触发条件"""
        total_tokens = self.count_tokens(self.messages)
        return total_tokens > self.max_tokens * 0.8  # 80%阈值
    
    def compress(self, mode: str = "hybrid") -> List[dict]:
        """
        两种压缩模式：
        1. 机械压缩（规则裁剪）：快但丢失信息
        2. 智能压缩（模型摘要）：准但贵且慢
        3. 混合压缩（生产推荐）：先用规则，再用模型精修
        """
        if mode == "mechanical":
            return self._mechanical_compress()
        elif mode == "intelligent":
            return self._intelligent_compress()
        else:  # hybrid
            return self._hybrid_compress()
    
    def _mechanical_compress(self) -> List[dict]:
        """
        机械压缩：按规则裁剪
        - 保留首尾消息（最重要）
        - 删除中间重复内容
        - 丢弃历史日志类消息
        """
        # 保留最近N轮 + 系统提示
        return self.messages[:3] + self.messages[-10:]
    
    def _intelligent_compress(self) -> List[dict]:
        """
        智能压缩：让模型总结历史
        优点：保留语义完整性
        缺点：贵，需要额外LLM调用
        """
        history = self._serialize_history()
        
        summary_prompt = f"""
        请总结以下对话的要点，保留关键信息和结论：
        
        {history}
        
        要求：
        1. 用简洁的语言概括每轮对话的核心
        2. 保留关键决策、用户偏好、待办事项
        3. 删除无意义的闲聊和重复内容
        """
        
        summary = llm.invoke(summary_prompt)
        
        # 返回摘要消息，替换原始历史
        return [
            {"role": "system", "content": "以下是之前的对话摘要："},
            {"role": "assistant", "content": summary},
            {"role": "system", "content": "以上是历史摘要，请在此基础上继续对话。"}
        ]
    
    def _hybrid_compress(self) -> List[dict]:
        """
        混合压缩（生产推荐）：
        1. 第一轮：机械压缩（快速过滤）
        2. 第二轮：模型摘要（精确提炼）
        平衡速度和效果
        """
        # Step 1: 机械压缩
        mechanical = self._mechanical_compress()
        
        # Step 2: 判断是否需要进一步智能压缩
        if self.count_tokens(mechanical) > self.max_tokens * 0.3:
            # 仍然太长，再用模型摘要
            return self._intelligent_compress()
        
        return mechanical
```

### 5.3 长期记忆：跨会话持久化

```python
class LongTermMemory:
    """
    长期记忆：跨会话持久化，存储在向量数据库/图数据库
    核心问题：存什么？存了怎么用？
    """
    
    def __init__(self, vector_db, graph_db=None):
        self.vector_store = vector_db  # Milvus/Pinecone
        self.graph_store = graph_db   # Neo4j（可选，存储关系）
    
    def store_interaction(self, user_id: str, 
                          interaction: dict):
        """
        存储用户交互到长期记忆
        触发时机：每次会话结束时
        """
        # 1. 提取关键信息（实体/关系/偏好）
        extracted = self._extract_memories(interaction)
        
        # 2. 存储到向量数据库（语义检索用）
        for memory in extracted["facts"]:
            self.vector_store.add(
                text=memory["content"],
                metadata={
                    "user_id": user_id,
                    "type": memory["type"],  # preference/fact/event
                    "timestamp": memory["timestamp"],
                    "importance": memory["importance"]
                }
            )
        
        # 3. 可选：存储到图数据库（关系推理用）
        if self.graph_store:
            for relation in extracted["relations"]:
                self.graph_store.add_relation(
                    subject=relation["from"],
                    predicate=relation["type"],
                    object=relation["to"],
                    properties={"confidence": relation["confidence"]}
                )
    
    def recall(self, user_id: str, 
               query: str, 
               top_k: int = 5) -> List[dict]:
        """
        召回与当前查询相关的长期记忆
        触发时机：每次新会话开始时
        """
        # 向量检索
        results = self.vector_store.search(
            query=query,
            filter={"user_id": user_id},
            top_k=top_k * 2  # 多召回一些，后面过滤
        )
        
        # 时间衰减：近期记忆权重更高
        scored = []
        now = datetime.now()
        for r in results:
            days_old = (now - r["timestamp"]).days
            recency_score = math.exp(-0.1 * days_old)  # 指数衰减
            importance_score = r["metadata"].get("importance", 0.5)
            final_score = r["score"] * recency_score * importance_score
            scored.append((r, final_score))
        
        # 按最终分数排序
        scored.sort(key=lambda x: x[1], reverse=True)
        return [r for r, s in scored[:top_k]]
    
    def _extract_memories(self, interaction: dict) -> dict:
        """
        从交互中提取结构化记忆
        使用LLM抽取实体、关系、偏好
        """
        prompt = f"""
        从以下对话中提取关键信息，结构化为记忆三元组：
        
        用户：{interaction.get('user_message')}
        助手：{interaction.get('assistant_message')}
        
        提取要求：
        1. 事实（fact）：用户提到的客观信息
        2. 偏好（preference）：用户的个人偏好
        3. 关系（relation）：用户与其他实体的关系
        4. 重要程度（1-5）：这个信息的重要程度
        
        返回JSON格式。
        """
        
        result = llm.invoke(prompt)
        return json.loads(result)
```

```python
class ModelGateway:
    """
    模型网关：统一入口，实现路由、限流、兜底
    """
    
    def __init__(self):
        self.providers = {
            "openai": OpenAIProvider(),
            "anthropic": AnthropicProvider(),
            "azure": AzureProvider(),
            "ollama": OllamaProvider(),  # 本地模型
        }
        self.fallback_chain = ["openai", "anthropic", "azure"]
    
    def chat(self, model: str, messages: list, 
             **kwargs) -> str:
        """
        统一调用入口
        """
        # 1. 路由到指定模型
        provider = self.providers.get(model)
        if not provider:
            model = "openai"  # 默认兜底
            provider = self.providers["openai"]
        
        # 2. 限流检查
        if not self.rate_limiter.allow(model):
            raise RateLimitExceeded(model)
        
        # 3. 调用（带超时）
        try:
            return provider.chat_with_timeout(messages, timeout=30)
        except TimeoutError:
            # 4. 熔断：超时切换到下一个模型
            return self._fallback(messages, model)
        except RateLimitError:
            # 5. 降级：触达限额切换
            return self._fallback(messages, model)
    
    def _fallback(self, messages: list, 
                  failed_model: str) -> str:
        """
        兜底链：模型A超时 → 切换模型B → ...
        """
        # 从失败模型的下一个开始尝试
        start_idx = self.fallback_chain.index(failed_model) + 1
        
        for model_name in self.fallback_chain[start_idx:]:
            try:
                provider = self.providers[model_name]
                return provider.chat(messages)
            except Exception as e:
                continue
        
        # 全部失败：返回降级响应
        return "当前服务繁忙，请稍后再试"
```

### 7.2 熔断机制工程实现

```python
import time
from enum import Enum
from dataclasses import dataclass
from typing import Callable, Any

class ErrorType(Enum):
    TIMEOUT = "timeout"
    PERMISSION_DENIED = "permission_denied"
    TOOL_NOT_FOUND = "tool_not_found"
    RATE_LIMIT = "rate_limit"
    UNKNOWN = "unknown"

@dataclass
class CircuitBreakerState:
    failure_count: int = 0
    last_failure_time: float = 0
    state: str = "closed"  # closed/open/half_open

class CircuitBreaker:
    """
    熔断器：防止Agent无限重试/循环
    三种状态：closed（正常）/open（熔断）/half_open（探测）
    """
    
    def __init__(self, 
                 max_failures: int = 5,
                 recovery_timeout: int = 60,
                 half_open_max_calls: int = 3):
        self.max_failures = max_failures
        self.recovery_timeout = recovery_timeout
        self.half_open_max_calls = half_open_max_calls
        self.state = CircuitBreakerState()
        self.half_open_calls = 0
    
    def call(self, func: Callable, *args, **kwargs) -> Any:
        """
        执行带熔断保护的函数
        """
        # 检查是否应该熔断
        if self.state.state == "open":
            # 检查是否超过恢复时间
            if time.time() - self.state.last_failure_time > self.recovery_timeout:
                self.state.state = "half_open"
                self.half_open_calls = 0
            else:
                raise CircuitBreakerOpen("Circuit breaker is OPEN")
        
        # 执行函数
        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise
    
    def _on_success(self):
        if self.state.state == "half_open":
            self.half_open_calls += 1
            if self.half_open_calls >= self.half_open_max_calls:
                # 连续成功，恢复正常
                self.state.state = "closed"
                self.state.failure_count = 0
    
    def _on_failure(self):
        self.state.failure_count += 1
        self.state.last_failure_time = time.time()
        
        if self.state.failure_count >= self.max_failures:
            self.state.state = "open"


class AgentExecutor:
    """
    Agent执行器：包含三层熔断保护
    """
    
    def __init__(self):
        # 1. 最大执行步数熔断
        self.max_steps = 20
        # 2. 单步超时熔断
        self.step_timeout = 30  # 秒
        # 3. 总任务超时熔断
        self.total_timeout = 300  # 秒
        # 4. 熔断器
        self.circuit_breaker = CircuitBreaker()
    
    def execute(self, agent, task: str) -> str:
        """
        执行Agent任务，带完整熔断保护
        """
        start_time = time.time()
        step_count = 0
        last_output = None
        
        while step_count < self.max_steps:
            # 检查总超时
            if time.time() - start_time > self.total_timeout:
                return self._handle_timeout(last_output, "total_timeout")
            
            # 执行单步
            try:
                output = self.circuit_breaker.call(
                    agent.step, task, timeout=self.step_timeout
                )
                last_output = output
                
                # 检查是否完成
                if output.is_final:
                    return output.content
                
                step_count += 1
                
            except CircuitBreakerOpen:
                return self._handle_error(last_output, "circuit_breaker_open")
            except TimeoutError:
                return self._handle_error(last_output, "step_timeout")
            except Exception as e:
                error_type = self._classify_error(e)
                return self._handle_error(last_output, error_type)
        
        # 超过最大步数
        return self._handle_error(last_output, "max_steps_exceeded")
    
    def _handle_error(self, last_output, error_type: str) -> str:
        """
        错误处理：根据错误类型决定如何处理
        """
        error_handlers = {
            ErrorType.TIMEOUT: "单步执行超时，请重试或简化任务",
            ErrorType.PERMISSION_DENIED: "权限不足，无法执行该操作",
            ErrorType.TOOL_NOT_FOUND: "工具不存在，请检查工具配置",
            ErrorType.RATE_LIMIT: "请求过于频繁，请稍后再试",
            "max_steps_exceeded": "任务过于复杂，已达到最大执行步数",
            "circuit_breaker_open": "系统过载，请稍后再试",
        }
        
        return error_handlers.get(error_type, "未知错误，请联系管理员")
    
    def _classify_error(self, error: Exception) -> ErrorType:
        """错误分类"""
        error_msg = str(error).lower()
        if "timeout" in error_msg:
            return ErrorType.TIMEOUT
        elif "permission" in error_msg:
            return ErrorType.PERMISSION_DENIED
        elif "not found" in error_msg:
            return ErrorType.TOOL_NOT_FOUND
        elif "rate limit" in error_msg:
            return ErrorType.RATE_LIMIT
        else:
            return ErrorType.UNKNOWN
```

### 7.3 面试回答模板

```
面试官：Agent需要哪些熔断机制？

满分回答：
"Agent失控是生产环境最大的风险之一。我设计了三层熔断：

第一层：最大执行步数。
防止Agent进入死循环，比如用户问一个模糊问题，
Agent反复查询工具但每次都觉得信息不够。
我会设置max_steps=20，超过就强制终止。

第二层：单步超时。
每次工具调用或LLM生成都有30秒超时，
防止单步卡死影响整个任务。

第三层：总任务超时。
整个任务有5分钟上限，
防止Agent处理复杂任务时无限消耗资源。

熔断后的错误处理也很重要：
- 超时→可以重试一次，还是超时就返回降级响应
- 权限拒绝→返回'无权操作，请联系管理员'
- 工具不存在→返回'该功能暂时不可用'

工程实现上，我用状态机管理熔断器状态：
CLOSE→OPEN→HALF_OPEN→CLOSE，
连续成功N次才恢复正常，防止误判。
"
```
