### 1️⃣ 检索阶段（00:00）

**Q: RAG检索相关问题有哪些？**

**A:**

#### 索引设计
- **数据结构选择**：根据数据特点选型——结构化数据用BM25，全文搜索用倒排索引，向量检索用 ANN 索引（HNSW/IVF）
- **分层索引**：冷热分离，热数据用内存索引（如Redis），冷数据用磁盘索引
- **索引更新策略**：全量重建 vs 增量更新，推荐 Lambda 架构（流式增量 + 定期全量合并）

#### BM25算法原理
- 基于TF-IDF的改进算法，核心公式：
  ```
  Score(D,Q) = Σ IDF(qi) × (tf(ti,D) × (k1+1)) / (tf(ti,D) + k1 × (1-b+b×|D|/avgdl))
  ```
- `k1`调节词频饱和度（通常1.2~2.0），`b`调节文档长度归一化（通常0.75）
- **优点**：对长文档友好，词频饱和避免过度依赖高频词

#### 向量检索实现
- **ANN算法**：HNSW（跳跃搜索图，适合在线）、IVF（倒排文件，适合批量）
- **量化优化**：PQ（乘积量化）压缩向量，节省内存90%+
- **混合检索**：密向量+稀疏向量（BM25）融合，Reciprocal Rank Fusion (RRF) 合并排名
- **离线向量化**：用BERT/Embedding模型批量生成，faiss/milvus存储

#### Rerank重排策略
- **Cross-Encoder**：用交叉编码器重新计算相关性分数，精度高但慢（用于精排阶段）
- **BGE-Reranker**：中文效果好的开源重排模型，支持长上下文
- **列表式重排**：Pointwise（各文档独立打分）→ Pairwise（两两比较）→ Listwise（全局最优）
- **业务规则融合**：时效性、权威性、用户偏好等业务信号加权

#### 截断策略处理
- **固定截断**：直接按token数截断，可能丢失关键信息
- **智能截断**：优先保留标题、开头、相关段落
- **语义分块**：按段落/句子分块，检索时返回完整相关块而非切割文档
- **动态窗口**：根据查询长度动态调整上下文窗口

### 2️⃣ 上下文工程（00:24）

**Q: 上下文工程考察什么？**

**A:**

#### 长度处理方式
- **Token预算管理**：预算分配（预算编码+预算压缩），固定上下文窗口内合理分配输入输出比例
- **摘要压缩**：用小模型对长上下文做摘要，保留核心信息
- **选择性注意力**：让模型学会"关注什么"，降低无关内容干扰
- ** Streaming Chunked Attention**：Longformer的稀疏注意力，O(n)复杂度处理超长文本

#### 上下文拼接结构设计
- **经典结构**：
  ```
  <system_prompt> + <examples> + <history> + <context> + <query>
  ```
- **层次化上下文**：全局上下文（系统级）→ 会话上下文（对话级）→ 即时上下文（当前查询）
- **信息密度排序**：最重要的放开头/结尾（位置编码权重），中间内容权重较低
- **动态组装**：根据查询类型动态选择上下文模块，避免无效信息

#### 如何避免性能下降
- **信息过滤前置**：检索阶段过滤无关内容，只召回高相关度文档
- **缓存复用**：相同上下文的请求复用KV Cache（如vLLM的PagedAttention）
- **分级上下文**：热数据放显存，冷数据放内存/磁盘，按需加载
- **估算先行**：处理前估算token消耗，超限时提前截断或拒绝

### 3️⃣ 记忆机制（00:34）

**Q: 记忆机制怎么设计？**

**A:**

#### 短期记忆 vs 长期记忆区分
- **短期记忆（Session Memory）**：
  - 只在当前会话有效，会话结束即清除
  - 实现：简单的轮次列表 + 最近N轮滑动窗口
  - 用途：保存当前对话上下文、用户当前意图
- **长期记忆（Persistent Memory）**：
  - 跨会话持久化，需要长期积累
  - 实现：向量数据库（Milvus/Pinecone）存储，摘要压缩存储
  - 用途：用户偏好、历史交互模式、领域知识

#### 存储方案
- **向量数据库**：存储用户交互记忆的embedding，支持语义检索
- **KV存储**：结构化记忆用Redis/Etcd（如用户画像、配置信息）
- **图数据库**：复杂关系用Neo4j（如用户→项目→任务→对话的链路）
- **混合存储**：向量存语义记忆，KV存结构化数据，图存关系记忆

#### 更新策略
- **写入时更新**：每次交互后立即更新记忆（如用户明确纠正）
- **定时汇总**：每隔N轮或N分钟，用LLM自动摘要并更新
- **阈值触发**：记忆长度超过阈值时触发压缩/摘要
- **遗忘机制**：设定记忆衰减（如7天未访问的记忆降权），定期清理低价值记忆

#### Function Calling设计
- **记忆读取（Read）**：根据当前查询从记忆中检索相关内容
- **记忆写入（Write）**：交互结束后自动写入关键信息
- **记忆删除（Delete）**：用户要求删除时，执行软删除（标记删除）而非物理删除
- **记忆检索（Search）**：支持语义检索 + 精确匹配混合查询

### 4️⃣ 任务规划（00:42）

**Q: Agent任务规划核心是什么？**

**A:**

#### 模型/规则驱动方案
- **规则驱动（ReAct-like）**：
  ```
  Thought → Action → Observation → Thought → ...
  ```
  - 优点：可控性强，可解释
  - 缺点：需要人工设计action space
- **模型驱动（Plan+Execute）**：
  - Planner模型负责分解任务，Executor模型负责执行
  - 适合复杂长任务，支持自反思
- **混合驱动**：简单任务用规则，复杂任务用模型

#### 工具调用顺序设计
- **串行执行**：按依赖顺序执行，适合有前后依赖的任务
- **并行执行**：无依赖的工具同时调用（如同时查天气+查股票），用 `asyncio.gather`
- **树状探索**：BFS/DFS探索任务空间，剪枝无效分支
- **优先级排序**：按工具成功率、速度、相关性排序

#### 失败处理与重试机制
- **重试策略**：指数退避（Exponential Backoff），最大N次重试
- **降级策略**：工具不可用时降级到备用方案（如搜索降级到百科）
- **自我修正**：ReAct循环中加入反思步骤（Reflection），检测失败后调整策略
- **异常分类**：区分可恢复错误（超时、网络波动）和不可恢复错误（权限不足、数据不存在）

### 5️⃣ 安全控制（00:50）

**Q: 安全控制有哪些考点？**

**A:**

#### Prompt注入攻击防御
- **输入过滤**：检测恶意指令模式（如"忽略之前指令"、"System:"前缀），用正则+小模型双保险
- **指令分离**：将用户输入与系统指令严格分离，不允许用户指令覆盖系统prompt
- **输出校验**：对模型输出做安全检测，防止敏感信息泄露
- **沙箱隔离**：危险操作（代码执行、文件操作）放在隔离环境

#### 输入过滤机制
- **关键词过滤**：黑名单词库 + 动态更新
- **语义过滤**：用分类模型判断输入是否包含恶意意图（如社工攻击）
- **格式校验**：JSON参数类型校验，防止注入Payload
- **长度限制**：防止超长输入导致上下文混乱

#### 工具调用安全
- **最小权限原则**：每个工具只授予必要权限
- **调用审计**：记录所有工具调用日志，便于事后审计
- **幂等设计**：危险操作支持幂等，避免重复执行造成损失
- **确认机制**：高风险操作（如删除、支付）需要用户二次确认

#### 权限控制设计
- **RBAC模型**：Role-Based Access Control，角色→权限映射
- **ABAC模型**：Attribute-Based Access Control，基于用户/资源属性动态决策
- **Token级别控制**：API Key绑定权限范围，支持细粒度权限配置
- **数据脱敏**：根据权限级别决定返回数据的脱敏程度

### 6️⃣ 限流算法（01:00）

**Q: 分布式限流怎么实现？**

**A:**

#### 分布式链式排桶限流
- **令牌桶算法（Token Bucket）**：
  - 系统以固定速率往桶里放令牌，请求消耗令牌
  - 允许突发流量（桶满时），同时限制长期平均速率
  - **Redis实现**：`Lua`脚本原子操作 `DECR` + `EXPIRE`
- **计数器算法**：简单直接，适合单机；分布式下有边界问题（请求突刺）

#### 漏桶算法 vs 滑动窗口算法
| 特性 | 漏桶算法 | 滑动窗口算法 |
|------|---------|-------------|
| 突发流量 | 不允许（匀速消费） | 允许（在窗口内） |
| 实现复杂度 | 低 | 中 |
| 精度 | 固定精度 | 窗口越小越精准 |
| 适用场景 | API限流、MQ削峰 | 限流墙、流量控制 |

- **滑动窗口日志**：记录每个请求时间戳，精确但内存消耗大
- **滑动窗口计数器**：将时间窗口分片（如1分钟分60个1秒桶），折中精度与性能

#### Redis数据结构应用
- **String (INC/DEC)**：简单计数器
- **ZSet（有序集合）**：滑动窗口限流，score存时间戳，成员存请求ID
- **Hash + Lua**：聚合统计，支持动态窗口
- **Stream**：Redis 5.0+，支持消息追踪与消费组

#### 误判率控制
- **缓存热点请求**：相同参数请求合并计数
- **分级限流**：用户级 → IP级 → 全局限流，逐级收紧
- **动态调整**：根据后端负载动态调整限流阈值
- **灰度发布**：新功能上线时放宽限流，观察稳定性

#### 索引失效处理
- **多级索引**：本地缓存 → Redis → 数据库，逐级穿透
- **异步更新**：写入时异步更新索引，避免阻塞主流程
- **兜底策略**：索引失效时降级为全表扫描或返回空结果
- **预热机制**：服务启动时提前加载热点数据到缓存

### 7️⃣ 评测系统（01:24）

**Q: 怎么设计Agent评测体系？**

**A:**

#### 评测维度定义
- **功能性**：工具调用准确率、任务完成率、步骤规划合理性
- **效率性**：响应时间、Token消耗、调用次数
- **安全性**：Prompt注入防御率、敏感信息泄露率、权限越界率
- **稳定性**：成功率、错误率、异常恢复能力
- **用户体验**：对话流畅度、回复可读性、错误提示友好性

#### 评测指标选择
- **任务完成指标**：
  - Task Success Rate（任务完成率）
  - Step Accuracy（每步执行准确率）
  - Path Efficiency（最优路径比率）
- **质量指标**：
  - Response Quality Score（人工评估/LLM评估）
  - Citation Accuracy（引用准确率，RAG场景）
  - Hallucination Rate（幻觉率）
- **效率指标**：
  - Latency（延迟）
  - Token Usage（Token消耗）
  - Tool Call Count（工具调用次数）

#### 数据集构建方法
- **人工标注**：专家设计测试用例，覆盖核心场景 + 边界case
- **自动化生成**：
  - LLM生成测试用例（Self-Instruct）
  - 从生产日志中挖掘真实用户query
  - 变异测试（对已有case做同义词替换、格式变换）
- **分层构建**：
  - 单元测试（单工具能力）
  - 集成测试（多工具协作）
  - 端到端测试（完整任务流程）
- **质量保证**：双盲标注、交叉验证、定期review更新

### 8️⃣ 优化思路（01:33）

**Q: 整体优化方向有哪些？**

**A:**

#### 提升相关度
- **检索层优化**：
  - Embedding模型微调（用领域数据训）
  - 混合检索调参（BM25权重 vs 向量权重）
  - 查询改写（Query Expansion/Rewrite）
- **重排层优化**：
  - 引入更多特征（文本相似度+字面匹配+业务信号）
  - 列表wise训练（Reranker微调）
- **生成层优化**：
  - Prompt工程优化，减少误解
  - Few-shot Examples精选

#### 检索阶段优化
- **索引优化**：分层索引、增量更新、冷热分离
- **查询优化**：拼写纠错、同义词扩展、查询意图分类
- **召回优化**：扩大召回候选集，减少漏召回
- **缓存优化**：热点query结果缓存，减少重复计算

#### 生成阶段优化
- **解码优化**：Beam Search → Nucleus Sampling，平衡质量与多样性
- **推理加速**：量化（INT8/INT4）、KV Cache压缩、投机解码
- **后处理优化**：规则校验、敏感词过滤、格式规范化
- **上下文优化**：信息压缩、去冗余、位置编码优化

#### 优化效果验证方法
- **A/B测试**：新旧方案流量对比，观察核心指标变化
- **回滚机制**：出现问题快速回滚，保证稳定性
- **金丝雀发布**：先放小流量验证，逐步放量
- **监控告警**：实时监控异常指标，分钟级发现回退

### 9️⃣ 数据处理（01:42）

**Q: 数据处理场景考察什么？**

**A:**

#### 数据规模扩大方案
- **水平扩展**：增加节点数，数据分片（如Hash分片、Range分片）
- **垂直扩展**：升级单机硬件（内存、CPU、SSD）
- **冷热分层**：热数据放内存/SSD，冷数据放HDFS/对象存储
- **数据归档**：历史数据归档到低成本存储，按需召回

#### 计算效率保证
- **批处理优化**：
  - 批量读写减少IO次数
  - 向量化计算（NumPy/Pandas）
  - 并行处理（Spark/Flink）
- **流处理优化**：
  - 异步Pipeline，减少阻塞
  - 背压机制（Back Pressure），防止数据积压
  - 状态管理优化，减少状态序列化开销
- **缓存策略**：
  - 多级缓存（本地缓存 + 分布式缓存）
  - 缓存预热，避免冷启动
  - 缓存穿透/击穿/雪崩防护

#### 稳定性保障
- **容错设计**：
  - 失败重试 + 死信队列
  - 检查点（Checkpoint）机制
  - 幂等设计
- **监控告警**：
  - 核心指标监控（延迟、吞吐量、错误率）
  - 异常检测 + 自动告警
  - 链路追踪（TraceId串联全链路）
- **灾备方案**：
  - 多AZ部署
  - 数据跨机房同步
  - 自动故障转移

### 🔟 RAG性能优化（01:54）

**Q: RAG性能优化从哪些方向入手？**

**A:**

#### 解锁模型能力
- **上下文扩展**：支持更长上下文（如Longformer、RoPE位置编码），减少截断
- **能力激活**：通过Prompt引导模型激活特定能力（如"你是一个专业的RAG助手"）
- **微调优化**：领域数据微调，提升专业领域问答质量
- **模型蒸馏**：大模型知识蒸馏给小模型，降低推理成本

#### 系统加固方案
- **索引优化**：
  - 索引压缩（PQ量化）
  - 索引分层（粗排+精排）
  - 索引更新增量处理
- **检索稳定性**：
  - 多路召回（向量+关键词+知识图谱）
  - 兜底策略（检索失败时降级）
- **服务稳定性**：
  - 限流熔断
  - 超时降级
  - 重试机制

#### 缓存/并行优化
- **KV Cache复用**：相同Query复用计算结果
- **检索缓存**：热点文档embedding缓存
- **结果缓存**：高频Query结果缓存
- **并行流水线**：检索→重排→生成并行执行，减少等待
- **异步处理**：非关键路径异步化，加快响应

#### 上下文处理优化
- **上下文压缩**：只保留高权重信息，减少干扰
- **信息去重**：去除重复检索结果
- **优先级排序**：重要信息放首尾（位置编码权重）
- **滑动窗口**：长文档分块滑动检索，避免上下文截断

#### 减少干扰因素
- **噪声过滤**：过滤低相关度检索结果
- ** Prompt注入防御**：防止恶意指令干扰
- **格式规范化**：统一输入输出格式，减少解析错误
- **错误边界**：优雅处理异常，不让错误传播

## 📌 面试高频追问

### Q: RAG和Fine-tuning怎么选？
**A:** 
- **RAG适用**：知识更新频繁、需要溯源、可接受一定幻觉
- **Fine-tuning适用**：任务模式固定、需要强一致性、领域术语多
- **最佳实践**：RAG + Fine-tuning结合，RAG提供知识，FT提升任务能力

### Q: 向量数据库选型？
**A:**
| 数据库 | 适用场景 | 优点 | 缺点 |
|--------|---------|------|------|
| Milvus | 超大规模 | 支持混合检索、云原生 | 运维复杂 |
| Pinecone | 云原生 | 全托管、易用 | 成本高 |
| Chroma | 小规模 | 轻量、易部署 | 功能有限 |
| Weaviate | 中等规模 | 原生混合检索 | 社区小 |

### Q: Agent最难的部分是什么？
**A:**
- **任务规划**：复杂任务分解的准确性
- **自我纠错**：失败后能识别问题并调整策略
