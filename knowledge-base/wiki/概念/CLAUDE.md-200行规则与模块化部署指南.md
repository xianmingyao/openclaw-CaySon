# CLAUDE.md 超过200行后的优化与部署指南

> 标签：Claude_Code / 工程实践 / 上下文优化

## 🎯 这是什么

CLAUDE.md 是 Claude Code 的**项目说明书**，在每次会话开始时加载，贯穿整个会话。

**核心问题**：当 CLAUDE.md 超过约200行时，指令遵循度会显著下降——这是因为 Claude 的注意力不是均匀分布在整个文档上的，**靠后的规则会受到"惩罚"**。

---

## ⚡ 200行规则核心结论

### 📊 Token消耗速算

| 行数 | Token消耗 | 占比（假设200k上下文） |
|------|----------|----------------------|
| 50行 | ~400 tokens | 0.2% |
| 100行 | ~800 tokens | 0.4% |
| 200行 | ~1,500-2,000 tokens | ~1% |
| 500行 | ~5,000+ tokens | ~2.5% |

> **关键**：200行时已经消耗1.5k-2k tokens，在你打字之前！

### 🔴 超过200行的代价

**实测案例**（DEV Community）：
- 200行 CLAUDE.md → 代码质量降到 **79%**
- 拆成3个文件 → 质量回升到 **96.9%**

**根因**：
1. **位置衰减** — Claude 对文档末尾的内容关注度更低
2. **信号噪声比** — 越长越难区分重要/不重要指令
3. **上下文污染** — /compact 后部分指令可能丢失

### 🚨 膨胀信号

当你出现以下情况时，就该考虑拆分了：

| 信号 | 说明 |
|------|------|
| 行数超过150行 | 非精确阈值，但需要滚动多屏 |
| 出现低频内容 | 有些规则只在特定场景用到 |
| 指令被忽略 | Claude 开始"选择性失聪" |
| /compact 后丢失 | 压缩后重要规则消失 |

## ✅ 超过200行后最该做的事：模块化拆分

### 📁 Claude Code 配置层级架构

```
项目根目录/
├── CLAUDE.md                    # 项目说明书（常驻核心指令）
├── .claude/                     # 模块化配置目录
│   ├── rules/                   # 可切换的规则模块
│   │   ├── api-design.md        # API设计规范
│   │   ├── testing.md           # 测试规范
│   │   ├── security.md          # 安全规则
│   │   └── commit-style.md      # 提交规范
│   ├── skills/                  # 可复用技能包
│   │   └── tdd-skill.md         # TDD开发流程
│   └── memory/                   # AI自动记忆
│       └── project-learning.md   # AI从工作中学习到的
└── settings.json                 # 权限配置
```

### 🔄 CLAUDE.md vs Rules vs Skills 定位

| 组件 | 定位 | 触发方式 | 加载时机 |
|------|------|---------|---------|
| **CLAUDE.md** | 项目核心说明书 | 常驻 | 会话开始即加载 |
| **rules/** | 非核心但有用的规范 | 按需加载 | 需要时通过规则引用 |
| **skills/** | 自动化工作流程 | `/skill name` 调用 | 显式激活 |
| **memory/** | AI自动学习的经验 | 自动 | 随项目演进累积 |

## 🎬 触发场景：什么时候用哪个

### CLAUDE.md（常驻核心）
```
✅ 适合放：
- 项目简介和技术栈
- 核心编码规范
- 安全 invariants（安全红线）
- 代码风格要求
- 禁止做的事（危险操作）
```

### rules/（按需加载）
```
✅ 适合放：
- API 设计规范（仅API开发时需要）
- 测试覆盖率要求
- Git 提交规范
- 部署流程要求
- 低频但重要的规范
```

### skills/（显式调用）
```
✅ 适合放：
- TDD 开发流程
- Code Review 流程
- 发布工作流
- 数据库迁移流程
- 任何需要多步骤的标准流程
```

## ✅ 优点

| 优点 | 说明 |
|------|------|
| **上下文精简** | 200行以内，指令遵循度最高 |
| **按需加载** | 不常用的规范不浪费上下文 |
| **可维护性** | 规则变更不影响其他模块 |
| **团队共享** | 可以 git commit 协作 |
| **可验证** | 每个规则可以独立验证效果 |

---

## ❌ 缺点

| 缺点 | 说明 |
|------|------|
| **初始成本** | 需要花时间拆分和组织 |
| **碎片化** | 规则分散在多个文件 |
| **优先级模糊** | rules 之间的优先级需要手动指定 |
| **学习曲线** | 需要理解四层架构 |
| **迁移成本** | 已有大型 CLAUDE.md 迁移耗时 |

## 🕳️ 避坑指南

### 🔴 坑1：不要把所有规则都塞进 CLAUDE.md

**错误**：
```
CLAUDE.md (500行)
├── API规范
├── 测试规范
├── 安全规则
├── Git规范
├── 部署流程
└── 代码风格
```

**正确**：
```
CLAUDE.md (150行核心)
.claude/rules/api.md
.claude/rules/testing.md
.claude/rules/security.md
```

### 🔴 坑2：不要在 CLAUDE.md 里写"关于 CLAUDE.md 的规则"

**错误**：
```markdown
# CLAUDE.md
这条文件应该保持在200行以内...
每条规则都应该是可验证的...
```

**正确**：把这些元规则放到团队的文档里，而不是让 Agent 读取的文件里。

### 🔴 坑3：rules/ 目录不要超过10个文件

太多文件 = 难以管理。超过10个可以考虑合并或建立子目录。

### 🟡 坑4：不要忘记 /compact 的影响

/compact 可能会丢弃一些"长期记忆"。确保核心 invariants（安全红线）在 CLAUDE.md 靠前位置，或者在 rules/ 中明确标注。

## 🚀 部署最佳实践

### 1. 用 /init 初始化
```bash
/claude-code
/init
```
让 Claude 自动生成 CLAUDE.md 初稿，然后精简到200行以内。

### 2. 一行一行审查
读完每行自问：**"删掉这行输出会变吗？"**
如果不会 → 删。

### 3. 低频内容优先拆分
只在特定场景用到的规范 → 拆到 rules/

### 4. 安全 invariants 放最前
安全相关的硬规则放在 CLAUDE.md 靠前位置（top 50 lines），避免位置衰减。

### 5. 定期回顾
每隔一段时间回顾 CLAUDE.md，删除过时内容，补充新规则。
