## 1. 🎯 一句话理解

> 企业AI落地不是一步到位，而是**递进演化**的过程：
> 工具 → 知识库 → RAG → 本体化 → Agent
> 
> **核心逻辑**：量级提升后遇到瓶颈，本体化是突破瓶颈的关键。

## 3. ⚡ 第一阶段：工具（效率提升）

### 3.1 这是什么
各种AI工具、效率工具，解决单点效率问题。

### 3.2 常见工具类型
```
├── 文档工具：Notion、飞书文档、Obsidian
├── AI对话：ChatGPT、Claude、豆包
├── 图像生成：Midjourney、DALL-E
├── 代码助手：GitHub Copilot、Cursor
└── 自动化：Make、Zapier、n8n
```

### 3.3 痛点
- 工具孤岛，数据不互通
- 依赖个人使用习惯，难以沉淀
- 规模扩大后效率反而下降

### 3.4 升级信号
当工具数量>10个，团队开始问"这个在哪""那个怎么用"

## 4. 🔧 第二阶段：企业知识库（Zilliz Cloud搭建）

### 4.1 这是什么
将散落的文档统一入库，通过向量数据库实现语义检索。

**核心价值**：从"找关键词"升级到"找意思"

### 4.2 Zilliz Cloud快速上手

#### 第1步：注册 + 创建Cluster
```
1. 访问 https://cloud.zilliz.com
2. 创建Serverless Cluster：
   - Name: geo-knowledge
   - Region: ap-southeast-1
3. 记录 Public Endpoint + API Key
```

#### 第2步：安装SDK
```bash
pip install pymilvus langchain langchain-community
```

#### 第3步：创建Collection + Schema
```python
from pymilvus import MilvusClient, DataType

schema = MilvusClient.create_schema(
    auto_id=True,
    enable_dynamic_field=True,
)

schema.add_field(field_name="id", datatype=DataType.INT64, is_primary=True)
schema.add_field(field_name="content", datatype=DataType.VARCHAR, max_length=8192)
schema.add_field(field_name="embedding", datatype=DataType.FLOAT_VECTOR, dim=1024)
schema.add_field(field_name="source_doc", datatype=DataType.VARCHAR, max_length=512)

client.create_collection(
    collection_name="internal_kb",
    schema=schema,
    dimension=1024,
)
```

#### 第4步：文档Chunking + 写入
```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
)

chunks = text_splitter.split_documents(documents)

# 写入
client.insert("internal_kb", {
    "content": chunk.page_content,
    "embedding": get_embedding(chunk.page_content),
    "source_doc": "文档名称",
})
```

#### 第5步：语义检索
```python
# 查询
query_embedding = get_embedding("用户问题")
results = client.search(
    "internal_kb",
    data=[query_embedding],
    limit=5
)
```

### 4.3 三Collection架构
```
Zilliz Cloud
│
├── Collection: internal_kb ← 企业内部知识库
│ ├── 权限：按角色过滤（developer/tech_lead/delivery）
│ └── 用途：CC/Codex通过MCP按需查询
│
├── Collection: client_kb_{client_id} ← 客户品牌知识库
│ ├── 权限：只有对应客户的服务团队
│ └── 用途：内容生成时RAG注入品牌知识
│
└── Collection: meta_questions ← 语义问题库
  └── 用途：语义去重+问题推荐
```

### 4.4 痛点（第二阶段的瓶颈）
- **上下文丢失**：只检索相关文档，无法理解业务逻辑
- **规则散落**：业务规则分布在各处，无法复用
- **无法推理**：遇到跨领域问题就失效
- **数据孤岛**：ERP/CRM/OA数据打不通

### 4.5 升级信号
知识库检索准确率>80%，但用户开始问"为什么"而不是"是什么"

---

## 5. 📚 第三阶段：RAG调用知识库

### 5.1 这是什么
让AI工具通过RAG（检索增强生成）调用企业知识库。

### 5.2 MCP架构
```
Claude Code / Codex / 内容生成平台
    ↓
GEO Knowledge MCP Server
    ├── 认证：API Key → 识别角色
    ├── 查询：Embedding → 搜索Zilliz → 过滤权限 → 返回
    └── 写入：文档 → Chunking → Embedding → 存入Zilliz
    ↓
Zilliz Cloud（语义搜索） ←→ PostgreSQL（业务数据）
```

### 5.3 RAG核心流程
```
用户问题 → Embedding → Zilliz检索 → 相关文档 → LLM生成 → 回答
```

### 5.4 痛点（第三阶段的瓶颈）
- **业务语义不懂**：AI知道"是什么"，但不懂"为什么"
- **规则无法执行**：只能回答问题，无法触发业务动作
- **状态无法追踪**：无法理解对象的状态变化
- **跨系统难打通**：本体不在，AI无法理解系统间关系

### 5.5 升级信号
当问"为什么订单延期"时，AI只能列出原因，但无法追踪因果链

## 6. 🎯 第四阶段：本体化（业务语义层）

### 6.1 这是什么
本体(Ontology)是给企业业务建立的"AI能理解的业务地图"。

### 6.2 本体的核心组成
```
本体 = TBox（概念模型） + ABox（实例数据）

TBox（术语学/概念模型）
├── 类（Class）：业务对象的类型
│   ├── 订单、产线、设备、客户
├── 属性（Property）：对象的特征
│   ├── 数据属性：订单金额、产品数量
│   └── 对象属性：订单→客户、订单→产品
└── 关系（Relationship）
    ├── 订单 包含 产品
    └── 客户 所属 区域

ABox（实例数据）
├── 具体业务对象实例
│   ├── 订单#20260115、客户#宁采臣
└── 实例之间的关系
    ├── 订单#20260115 包含 产品#P100
```

### 6.3 企业AI Agent的7层架构
```
┌─────────────────────────────────────────────────────────────┐
│                  企业AI Agent 7层架构                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   第7层：Agent层           用自然语言和人协作的层面           │
│   第6层：编排层           决定任务怎么执行                   │
│   第5层：服务层           把业务能力变成Agent可调用的工具     │
│   第4层：规则层           根据规则判断业务状态是否异常        │
│   第3层：数据层           根据本体对象查询真实系统的数据      │
│   第2层：本体层           回答业务世界有什么、怎么关联、什么状态│
│   第1层：语义层           将用户自然语言映射到统一业务对象     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.4 本体的价值
| 仅有RAG | 引入本体后 |
|---------|-----------|
| AI只能回答资料问题 | AI能进行业务价值分析 |
| 无法解决经营问题 | 能发现"订单增长但毛利下降"的原因 |
| 老板问利润下降，AI只能查文档 | AI能追踪因果链 |

### 6.5 痛点（第四阶段的瓶颈）
- **建模成本高**：需要业务+技术专家深度协作
- **维护复杂**：业务变化需要同步更新本体
- **规模挑战**：大型企业本体可能非常庞大

### 6.6 升级信号
本体稳定运行，团队开始问"能不能自动执行"

## 7. 🚀 第五阶段：Agent（执行闭环）

### 7.1 这是什么
让AI不仅能回答问题，还能**执行动作、闭环追踪**。

### 7.2 Agent执行架构
```
用户请求 → 语义层 → 本体层 → 数据层 → 规则层 → 服务层 → 编排层 → Agent层
              ↓         ↓        ↓        ↓        ↓        ↓        ↓
           理解"大订单" 定位对象  查数据   筛选问题  聚合结果  组装回答  自然语言
```

### 7.3 Agent vs 传统系统
```
传统客服：知识库检索 → 给出答案
本体Agent：理解问题 → 查本体(购买历史/偏好/状态) → 执行退换货/优惠
```

### 7.4 规则引擎兜底
```python
# 本体规则示例：订单风险评估
RULE OrderHighRisk:
    IF 订单.金额 > 100万
    AND 订单.账龄 > 30天
    AND 客户.信用等级 == "C级"
    THEN:
        订单.风险标记 = "高风险"
        触发.发送通知(接收人=销售总监)
        触发.锁定订单审批(审批人=总经理)
```

## 10. 🕳️ 避坑指南

### 坑1：跳过知识库直接做Agent
**问题**：没有知识沉淀，Agent只能胡说八道
**解决**：先搭知识库，再谈Agent

### 坑2：一步到位做全量本体
**问题**：试图一次性建立完美本体，项目难产
**解决**：从最小本体开始，聚焦核心场景，快速迭代

### 坑3：本体和技术栈强耦合
**问题**：本体实现绑定特定技术平台
**解决**：本体用标准语义模型（OWL/RDF），技术选型解耦

### 坑4：缺乏业务专家参与
**问题**：纯技术团队建模，业务语义失真
**解决**：业务专家全程参与，本体评审必须业务签字

### 坑5：忽略本体维护成本
**问题**：上线后本体无人维护，逐渐失效
**解决**：建立本体运营机制，纳入业务部门KPI

| 第5阶段 | Agent | 执行闭环 | 自动化需求 |

### 一句话总结：
> **工具是起点，知识库是基础，RAG是增强，本体是突破，Agent是闭环。**
